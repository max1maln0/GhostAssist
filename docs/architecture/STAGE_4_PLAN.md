# Stage 4 — Multi-Provider AI: план и архитектурные решения

Статус: **Stage 4.1–4.2 реализованы; Stage 4.3 и далее — план**. [Фактическая архитектура Registry](PROVIDER_REGISTRY.md). Исходная база — подтверждённый main
`d85c349cde79e5b66c17900a47c867f10cd3b9b4`.
Windows CI базы: [Python 3.10–3.12, success](https://github.com/max1maln0/GhostAssist/actions/runs/42362659203).
Stage 4.1 добавил реальный Provider Registry, независимые runtime-привязки и проверки возможностей моделей. Stage 4.2 добавил [OpenAI Responses/Transcriptions](OPENAI_PROVIDER.md), независимые настройки и схему 2; рабочие адаптеры — Gemini и OpenAI. Следующие разделы описывают дальнейший план и не означают реализацию новых провайдеров.

## Сохранить из Stage 3

ApplicationController и TaskOrchestrator сохраняют владение операциями, UUID,
ожиданием подтверждения, отменой и историей. Платформенные адаптеры и VAD FIFO
не зависят от выбора AI. Новые SDK должны оставаться в providers/ и подключаться
через существующие AIProvider / TranscriptionProvider. Сначала расширяются
контракты и тесты, затем отдельные адаптеры; второй контроллер задач не нужен.

## Provider Registry и точка сборки

Реестр хранит доверенные идентификаторы и фабрики адаптеров. Не загружать Python
модули, классы или выражения по строкам пользовательской конфигурации.
Регистрация и проверка выполняются при сборке зависимостей; runtime получает
проверенный снимок выбранных привязок. Не создавать сетевые клиенты всех
провайдеров заранее. Явно определить владение клиентом и close, включая отмену,
ошибку и завершение службы. Не добавлять неограниченные потоки.

Генерация и транскрибация получают отдельные привязки `(provider_id, model_id)`.
Провайдер может реализовывать один или оба контракта. Фасад должен уметь
делегировать этим двум зависимостям, сохраняя существующий интерфейс сценариев.
Маршрутизация не должна менять UUID записи → транскрибации → подтверждения → ответа.

Поток: пользовательский ввод → ApplicationController → TaskOrchestrator →
привязка задачи из реестра → провайдерный контракт → адаптер SDK/HTTP →
TaskEvent → контроллер → ViewEvent. Только успешный итог сохраняется в историю.

## Возможности моделей

Разделить возможности адаптера и конкретной модели: текст, изображения,
транскрибация/аудиоввод, streaming и ограничения размеров. Начать с возможностей,
нужных существующим сценариям; tools и structured output не подключать без задачи.
Для каждого признака указывать источник: проверенные локальные сведения,
обнаруженные метаданные или явное пользовательское описание custom-модели.
Не выдавать статический флаг Gemini за гарантию любой модели.

Проверять совместимость до захвата/отправки; несовместимая привязка должна давать
понятную типизированную ошибку. Список моделей и проверка доступа запускаются
явным действием, выполняются в фоне с тайм-аутом, не блокируют Tk и не передают
содержимое разговора. Получение списка само по себе не доказывает поддержку vision
или транскрибации. Live-пробы с данными/расходами требуют отдельного действия.

## Конфигурация и ключи

Stage 4.2 ввёл схему 2 с миграцией версии 1 без потери Gemini-значений и обновил .env.example. Следующие переходы проектировать отдельно, сохраняя этот механизм.
Планируемые группы: общие параметры AI, реестр настроенных подключений,
привязки генерации/транскрибации, параметры каждой интеграции. Подключение содержит
identifier, model, endpoint при необходимости, request timeout и SecretStr-поля
авторизации; сырые ключи не помещать в поля истории, профили и UI-события.

Сохранить приоритет явных аргументов / environment / dotenv / defaults,
межпроцессную транзакцию, атомарную запись с ACL и восстановление backup.
Маскировать ключи в Dashboard; загрузка ключа не должна выводить его в repr,
лог, исключение, URL или диагностический экспорт. На первом этапе можно
сохранить защищённый .env; отдельное системное хранилище ключей — отдельное решение
с миграцией, а не неявное изменение формата.

Изменение провайдера применять контролируемым перезапуском службы, как текущие
параметры Gemini. Старые задачи завершаются/отменяются по существующим правилам;
их результаты не попадают в новую сессию или привязку.

в этом плане. Тяжёлые модели и отдельные серверы не добавлять в дистрибутив.
Ollama остаётся отдельно устанавливаемым пользовательским сервисом.

## Сеть, доверие и fallback

- Общий бюджет задачи включает все попытки и backoff; сетевой тайм-аут каждой
  попытки ограничен оставшимся бюджетом. Существующая отмена продолжает отсекать
  поздние результаты, а клиент освобождает соединения в finally/context manager.
- Авторизация, квоты, сеть, timeout, несовместимость и недоступность модели
  отображаются через общие коды; ошибки SDK и тела ответов не показываются напрямую.
- Перед сменой модели очищать partial output. До успешного завершения fallback
  не сохранять отдельные частичные взаимодействия в историю.
- Межпровайдерный fallback по умолчанию выключен. Нельзя автоматически отправлять
  аудио, снимок или историю другой организации без явной настройки пользователя.
  Проверять совместимость модальностей и разрешённые направления передачи данных.
- Custom endpoint — явная доверенная настройка. Валидировать схему/host/port,
  запретить credentials в URL; TLS-проверка включена. Не пересылать Authorization
  через redirect на другой origin. HTTP для локального сервиса допускается только
  осознанно; удалённые Ollama endpoints требуют отдельного выбора.
- Не принимать URL из текста ответа модели как команду изменения подключения.
  Сохранять origin-изоляцию ключей и не смешивать заголовки разных подключений.

## Dashboard

Добавить компактные отдельные привязки «Ответ» и «Транскрибация», доступные модели,
индикатор совместимости и masked-редактор ключа текущего подключения. Discovery и
проверка подключения имеют отмену, deadline и bounded queue. Во время операции
показать выбранные provider/model; ошибки не меняют сохранённую конфигурацию
частично. Все Tk-операции выполняются главным потоком. Не менять тёмную стилистику
и существующий редактор горячих клавиш ради этой интеграции.

## Тесты и критерии приёмки

1. Registry: известный/неизвестный id, фабрики, отсутствие побочных сетевых вызовов,
   отдельные generation/transcription, закрытие клиента после ошибки и отмены.
2. Возможности: несовместимые модальности, неизвестная custom-модель, ограничения
   размера, безопасное поведение при устаревших метаданных.
3. Для каждого адаптера: mock HTTP/SDK streaming, пустой и неполный ответ,
   401/403/429/5xx, timeout, backoff в общем бюджете, отмена и очистка клиента.
4. Конфигурация: миграция схемы 1, идемпотентность, env-приоритет, секреты,
   DACL, конкурентные записи, откат при ошибке и совместимость Dashboard.
5. Интеграция: экран, ручное аудио, подтверждение, VAD FIFO, история,
   provider switch при активной задаче, отсутствие поздних результатов и
   смешивания ключей/провайдеров. Тест запрета неразрешённого fallback.
6. Полная регрессия Python 3.10–3.12, Ruff, форматирование, compileall и Windows CI.
   Автотесты не требуют сети, ключей, платных запросов или устройств.
7. Отдельная opt-in live-приёмка каждого подключения с тестовыми данными и
   зафиксированными затратами/задержками; не выдавать mocks за проверку API.

Разделять реализацию на логические коммиты, проверять и отправлять каждый этап.
Не переносить аппаратные ограничения Stage 3 в список успешно проверенных функций.
Stage 4 считается готовым только после реальной реализации этих критериев;
наличие этого документа не означает поддержку Claude, Ollama или custom API. OpenAI реализован в Stage 4.2 в описанном объёме.
