# Фактическая архитектура GhostAssist

Dashboard (CustomTkinter) управляет настройками `.env`, профилями и дочерней службой. Трей и глобальная клавиша передают команды в очередь главного потока Dashboard; stdin дочернего процесса используется для отмены и завершения. Windows named mutex ограничивает число экземпляров.

Служба `main.py` принимает глобальные клавиши и кнопки мыши через pynput, передаёт команды в очередь Tk и управляет `TaskState`. Два ограниченных executor выполняют обработку и VAD-захват; только главный поток обновляет HUD и окна. Отмена устанавливает событие, запоздавшие результаты игнорируются.

Windows-адаптер аудио захватывает WASAPI loopback и формирует WAV в RAM; WebRTC VAD и ограниченная очередь в `core/audio_queue.py` разделяют реплики. `LLMWorker` — временный фасад прежних сигнатур, делегирующий запросы интерфейсам из `core/provider_contracts.py`. `GeminiProvider` и его клиент в `providers/` инкапсулируют SDK, потоковую генерацию, ограниченный fallback моделей, тайм-ауты и отмену. Полноэкранный путь: оркестратор → экранный адаптер → фасад → AIProvider → GeminiProvider; аудиопуть использует TranscriptionProvider. Тестовый MockProvider не обращается к сети. `ContextManager` формирует инструкции, `SessionManager` хранит историю в RAM.

Контракты `core/platform_contracts.py` задают ScreenCapture, AudioCapture и HotkeyBackend. Windows-реализации находятся в `platform_adapters/windows/`; `composition.py` собирает оркестратор, провайдер, экран, аудио и обработчики и передаёт их службе. Dashboard использует те же адаптеры аудио и клавиатуры. Контракт экрана принимает прямоугольники с отрицательными координатами; Windows DPI awareness и ограничение размера остаются в платформенном слое.

Платформенная независимость относится к выделенным контрактам и ядру, но приложение целиком ещё зависит от Windows: Tk HUD и выделение используют Win32, настройка горячих клавиш использует pynput, трей и жизненный цикл процессов требуют платформенных адаптаций. Реализаций macOS/Linux пока нет; для них нужны экранный и аудиозахват, обработчики ввода, управление окнами и разрешениями.

Настройки читаются Pydantic из `.env` и окружения, обновление файла атомарное; пользовательские профили хранятся в `config/profiles`. Сетевые запросы отправляют необходимые снимки, звук, текст и контекст Gemini. Stage 3.1 добавляет независимые доменные контракты, пока не заменяя существующий жизненный цикл.

Stage 3.2: полноэкранный захват выполняет `TaskOrchestrator`, который владеет состоянием, отменой, тайм-аутом и ограниченной очередью событий. Главный поток опрашивает события и обновляет HUD и память; оркестратор удерживает допуск до выхода обработчика. В `GhostAssistApp` проверка `screenshot_id`, `TaskState` и состояния VAD в единственном Tk-потоке не допускает конфликтующие операции. Выделение области, запись и аудиоочередь продолжают использовать `TaskState`. При закрытии отправляется отмена; если фоновый обработчик не завершился за три секунды, служба пишет диагностику. Управляемую зависшую службу Dashboard завершает после тайм-аута; поток Python нельзя безопасно принудительно остановить.

Возможности проверяются по декларации адаптера для поддерживаемых типов входа, а не динамическим запросом метаданных конкретной произвольной модели. Выбранная пользователем модель может быть недоступна или поддерживать иные входы; ошибка запроса обрабатывается провайдером. Автоматического переключения на сторонних AI-провайдеров нет.
