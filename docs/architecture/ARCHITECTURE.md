# Фактическая архитектура GhostAssist

`main.py` — Tk-адаптер и процессная точка входа: глобальные обработчики передают команды в очередь, главный поток вызывает контроллер и отображает типизированные ViewEvent. Только UI создаёт HUD, выделение и окно проверки транскрипции. Dashboard, трей и stdin управляемой службы сохраняют прежний протокол. Windows mutex ограничивает экземпляры.

`core/controller.py` содержит независимый ApplicationController: допуск операций, режимы TEST/INTERVIEW, снимки, выделение, ручное аудио, транскрибацию, подтверждение, обработку VAD-сегментов, отмену и историю. Он получает зависимости через `platform_adapters/windows/composition.py` и не импортирует Tkinter, Windows API или Gemini SDK.

Все пользовательские операции выполняет один TaskOrchestrator с одним executor. CREATED резервирует выделение; RUNNING выполняет обработчик; WAITING ожидает подтверждение транскрипции без занятого потока; COMPLETED, FAILED и CANCELLED завершают операцию. Одна запись, её транскрипция, редактирование и ответ сохраняют UUID. Возобновление допускается только после выхода предыдущего обработчика. Каждый запуск фазы получает отдельный номер: запоздавший таймер транскрибации не завершает генерацию с тем же UUID. Необработанные события и занятый executor не позволяют начать следующую операцию. TaskState удалён.

Длительный VAD-источник имеет отдельный executor и событие остановки; его FIFO ограничена числом и суммарными байтами сегментов. Источник продолжает захват при транскрибации, проверке текста и генерации. Контроллер запускает сегменты строго последовательно через общий оркестратор. Глобальная отмена останавливает источник, очищает очередь и отменяет операцию; отмена окна проверки отклоняет одну реплику. Допуск экрана закрыт до остановки источника и завершения очереди.

Рабочие обработчики публикуют только TaskEvent. Controller.poll принимает их в порядке публикации, проверяет UUID и отмену, сохраняет только успешные ответы в SessionManager и возвращает ограниченный набор ViewEvent для GUI. Обычные промежуточные события могут вытесняться, финальное событие остаётся последним и не перезаписывается новой задачей. Приватные тексты скрыты в repr доменных событий.

Windows-адаптеры содержат MSS/Pillow, WASAPI, pynput hook, DPI и mutex. Контракты платформы и очередь аудио остаются в core. `LLMWorker` получает отдельные AIProvider/TranscriptionProvider. Точка сборки Stage 4.1 подключает BoundGeneration и BoundTranscription к ленивому Provider Registry; фабрика выбирается по доверенному ID, модель — независимой привязкой. Только providers/ содержит SDK. Stage 4.2 регистрирует Gemini и OpenAI, разрешая обе независимые привязки из конфигурации. ProviderCapabilities адаптера отделены от ModelCapabilities конкретной модели. Неизвестные возможности, несовместимые форматы и превышение размера блокируют отправку до SDK. OpenAI Responses и Audio Transcriptions реализованы; Переключатель Gemini/OpenAI реализован в Dashboard 2.0; Claude/Ollama отложены.

Настройки Pydantic читают `.env` и окружение, профили остаются Markdown. История и аудио хранятся в RAM; ключ остаётся локальным в `.env`. Stage 3.6 ввёл схему 1, Stage 4.2 мигрирует её в схему 2: `load_settings` проверяет и атомарно мигрирует legacy-файл, а `Settings.groups` предоставляет неизменяемые логические представления. Плоские имена сохранены для совместимости. Gemini использует группу ProviderConfig; OpenAI получает отдельный SecretStr-ключ и привязки; секреты провайдеров не смешиваются. Подробности и полный перечень полей: [CONFIGURATION.md](CONFIGURATION.md).

При закрытии контроллер отменяет задачу и источник; UI ожидает освобождения до трёх секунд, затем уничтожает окно и возвращает управление. `shutdown(wait=False)` не останавливает работающие executor-потоки. Поэтому консольные точки входа main.py и ui.dashboard до тяжёлых импортов создают Windows ProcessGuard: отдельный наблюдатель владеет анонимным Job Object и наследуемым дескриптором владельца. Выход или Ctrl+C запускает бюджет шесть секунд, после которого завершается только эта группа процессов (код 124). Штатный выход не ждёт истечения бюджета. Dashboard дополнительно ограничивает ожидание управляемой службы четырьмя секундами. Зависший нативный вызов не прерывается внутри потока; при отмене задачи ресурс может оставаться занят до перезапуска службы. Библиотечный ApplicationController сам не создаёт процессов и не завершает процесс вызывающей стороны.

Stage 3.1–3.6 завершены по автоматическим критериям. Финальная проверка конфигурации включает DACL staging/замены, частичный отказ ReplaceFileW, межпроцессные миграции и сохранения. Результаты и аппаратные ограничения: [финальный аудит](../audits/STAGE_3_FINAL_AUDIT.md).

Stage 4.1: [Provider Registry](PROVIDER_REGISTRY.md) описывает владение клиентами, close, независимые привязки, модельные ограничения и проект следующей конфигурационной итерации. Стандартная сборка регистрирует Gemini и OpenAI; при отсутствии новых полей оба legacy defaults берутся из существующего GEMINI_MODEL. Контроллер не выбирает провайдера и при завершении вызывает только общий owner.close зависимостей.

Stage 4.2: [OpenAIProvider](OPENAI_PROVIDER.md) использует request-scoped AsyncOpenAI и HTTP-клиент в собственном event loop, bounded retry/deadline и явное закрытие stream. Четыре поля .env выбирают независимые привязки. Контроллер и оркестратор не изменялись; отложенные результаты, WAITING, история и VAD используют прежний механизм.

## Dashboard 2.0 (Stage 4.2.1)

[Состав страниц и lifecycle](DASHBOARD_2.md). `ui/dashboard.py` собирает семь страниц, тему и общие компоненты. SettingsActions, ProfileActions, HotkeyActions и ServiceActions отвечают за соответствующие пользовательские действия. Три ограниченных JobRunner-канала выполняют запись конфигурации/проверку hooks, проверку метаданных API и сканирование WASAPI; результаты принимает главный Tk-поток. Контроллер и оркестратор пользовательских AI-задач не менялись.

Страницы строятся лениво: Overview сразу, остальные один раз при открытии. Общие переменные формы существуют независимо от виджетов. Навигация скрывает только предыдущую страницу, сохраняет экземпляры и прокрутку. DeferredOptionMenu локально откладывает принудительный idle-flush CTk; ScrollbarBridge коалесцирует обновления и отменяет свой таймер при уничтожении. Метрики содержат только длительности, без конфигурации и разговоров.

Управляемый stdin IPC дополнен командами H (HUD), D (позиция), M (режим). Служба отправляет READY с непрозрачной сигнатурой конфигурации и привязками, STATE с режимом/HUD/записью, SESSION со счётчиками и фиксированный ERROR без тела исключения. Читатель ограничивает строки и очередь; результат привязан к объекту текущего дочернего процесса. READY отправляется после установки системных hooks. Внешние процессы не управляются.
